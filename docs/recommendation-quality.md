# 추천 품질 기준 · evaluation-v1

## 평가 입력과 기대값

공고는 기존 `backend/src/main/resources/seed/job-postings.json`의 **가상 공고 40개**다.
프로필과 기대 순서는 `backend/src/test/resources/evaluation/profiles-v1.json`에 별도로 작성했다.
기준 날짜는 **2026-09-29**, 공고 JSON의 줄바꿈을 LF로 정규화한 SHA-256으로 입력을 고정한다.
`OPEN`이고 마감일이 지나지 않은 36개만 순위를 매기며, 마감/종료된 4개도 점수·설명 회귀 검증에 포함한다.
40개 × 10개 프로필 = **400개 점수·근거·누락 설명**을 기준 파일에 저장한다.

| 프로필 | 검토 목적 | 기대 상위 그룹 (그룹 간 우선순위, 그룹 내 무순서) |
| --- | --- | --- |
| backend-junior | Java 신입, 필수 기술·서울 선호 | 001 → 029 → {015,023,031} |
| backend-aliases | 위 프로필의 별칭·공백·지역 표현 동등성 | 위와 같음 |
| backend-experienced | 결제 API 3년 경력, Kafka·Redis | {003,021} → {007,035} → 019 |
| frontend | React 프로젝트, 부산 선호, 필수 기술 우선 | 008 → {012,030} |
| data-analyst | SQL·Python·Pandas 프로젝트, 서울 선호 | 004 → 022 → {016,032} |
| ai-nlp | 문서/콘텐츠 프로젝트의 업무 의미 | 036 → 020 → 026 |
| devops | 배포 프로젝트와 희망 직무 | 002 → 018 → 034 |
| short-experience | 6개월 경력과 신입/경력 3년 공고 차이 | {001,029,035} → {003,021} |
| project-only | 프로젝트 점수와 선언 기술 누락 구분 | {001,029} → {015,023,031} |
| no-skills | 기술 근거가 없을 때 희망조건만 반영 | {001,003,007,017,021,029,035} |

번호는 `onfit-` 접두사를 생략했다. 기대 그룹은 상위 후보에 대한 **부분 순서**이며,
판단하지 않은 나머지 공고를 부적합으로 확정하지 않는다. 그룹 내에서도 개별 쌍의 기대가 있으면
JSON의 `judgments`를 사용한다(예: 프론트엔드 012 > 030은 동일 기술 조건에서 부산 선호를 적용한다).
이 기준은 가상 시나리오에서 작성한 선호 가설이다. 실제 사용자 선호나 채용 전문가가 확정한 정답은 아니다.

기대 순위는 현재 점수 출력에 맞춰 작성하지 않았다. 예를 들어 서울 선호 데이터 분석 프로필은
004를 032보다 우선하도록 정했지만, 현재 계산기는 우대 기술 영향으로 032를 먼저 올린다.
별도로 작성한 **33개 기대 쌍과 이유**로 개선/악화를 확인하며, **20개 부분 점수·기술 목록 기대값**으로
계산과 설명의 동작을 확인한다. 기술 별칭 프로필은 동일 입력 검증 사례이므로 독립된 선호 표본으로 합산하지 않는다.

## 점수·설명 검토 결과

- 필수 기술 35%, 우대 기술 20%, 의미 유사도 20%, 경험 15%, 희망조건 10%가 운영 기준이다.
  부분 점수는 소수 둘째 자리 HALF_UP으로 계산한 뒤 가중 합산을 다시 둘째 자리로 반올림한다.
  따라서 66.67 두 항목을 합산한 결과가 53.34처럼 나타날 수 있다.
- 필수/우대 기술은 공백·대소문자·별칭을 정규화한 이름으로 비교한다. 결과에는 공고의 기술 표시명을 남긴다.
  Java와 JavaScript는 서로 다른 기술이다. 프로젝트의 전각 쉼표/세미콜론을 처리하고 CI/CD는 쪼개지 않는다.
- 선언된 기술과 프로젝트 기술은 별도로 반영한다. 프로젝트만 적은 프로필은 경험 점수를 얻어도
  `matchedRequiredSkills`는 비고 `missingSkills`에는 필수 기술이 모두 남는다.
  현재 프론트 프로필 저장은 프로젝트 기술을 보유 기술 목록에도 포함하므로 해당 시나리오는 API 직접 입력의 경계 사례다.
- 직무 경력이 정확히 일치하면 경험 점수는 100점이다. **경력 기간·공고 요구 연차는 현재 비교하지 않는다.**
  6개월 경력과 3년 경력을 구분하지 못하는 기대 쌍을 숨기지 않고 미충족으로 남긴다.
- 직무 경력 일치가 없으면 프로젝트 중 필수 기술 포함률이 가장 높은 프로젝트를 사용한다.
  여러 프로젝트의 기술을 합쳐 경험 점수를 부풀리지 않는다.
- 희망 직무 50점, 희망 지역 50점으로 희망조건 부분 점수를 계산한다. 서울특별시/서울시 등은 최상위 지역으로 맞춘다.
  경기 광주시는 광주광역시로 간주하지 않는다. 지역은 현재 가산점이며 강제 제외 조건이 아니다.
- `missingSkills`는 **필수 기술 누락만** 표시한다. 우대 기술 누락은 `matchedPreferredSkills`와 공고 목록으로 비교한다.
- 기술 근거가 없으면 기술/경험 점수는 0점이다. `no-skills` 프로필의 순위는 희망조건과 동점 처리 결과일 뿐
  취업 가능성이나 높은 적합도를 뜻하지 않는다.
- 공고 기술 목록 자체에 동의어 중복이 들어오면 현재 분모에 중복 반영될 수 있다. 이번 40개에는 그런 중복이 없다.
  실제 수집 단계에서는 필수/우대 기술별 정규화 후 중복 제거가 필요하다.
- 이 문서의 `evaluation-v1` 기준 점수는 의미 유사도 0점이므로 최고 점수가 80점이다.
  AI 연동 결과와 남은 ai-nlp의 020 > 026 미충족 사례는 [3단계 평가](semantic-integration.md)에 기록했다.

## 재현·비교 방법

`backend` 디렉터리에서 실행한다.

```powershell
./gradlew.bat test
./gradlew.bat recommendationEvaluation
```

평가 실행은 DB/Docker/네트워크/현재 날짜를 사용하지 않는다. **실제 운영 계산기**를 호출하며 별도 계산식을 복제하지 않는다.
동점은 고정된 seedKey 오름차순으로 처리한다. 이는 새 DB에서 순서대로 시딩한 API의 ID 정렬과 같다.
기존 DB의 서로 다른 ID 배정까지 동일한 동점 순서를 보장하는 것은 아니다.
반복 실행과 공고 입력 순서 역전에도 점수·근거·순위가 동일함을 테스트한다.

생성 파일은 `backend/build/reports/recommendation-evaluation/`에 있다.

- `baseline.json`: 현재 운영 가중치의 400개 결과.
- `candidate.json`: 실험 가중치의 같은 입력 결과.
- `comparison.md`: 프로필별 Top5, 기대 쌍 충족, 개선/악화/미충족 이유, 바뀐 전체 순위와 부분 점수.

`baseline-v1.json`은 소스에 고정된 승인 기준 결과다. 테스트는 새 계산 결과와 이 파일 전체를 비교한다.
평가 명령은 승인 기준 파일을 자동으로 덮어쓰지 않는다. CI에서도 평가와 기존 API 테스트를 실행하고 보고서를 보관한다.

별도 후보 JSON으로도 비교할 수 있다.

```json
{"required":0.35,"preferred":0.05,"semantic":0.20,"experience":0.10,"preference":0.30}
```

```powershell
./gradlew.bat recommendationEvaluation -PevaluationWeights=path/to/weights.json
```

각 가중치는 0~1이며 합계는 1이어야 한다. JSON의 다섯 필드는 모두 필수다.
후보 파일 경로는 backend 기준이며 실험 결과는 운영 API의 가중치를 바꾸지 않는다.

## 변경 판단

- **기대 쌍 충족**: `higher` 공고의 총점이 `lower` 공고보다 엄격히 높아야 한다. 동점은 미충족이다.
  ID 때문에 우연히 먼저 표시된 것을 품질 개선으로 세지 않는다.
- **기대 공고 Top5 포함**: 그룹에 적힌 공고 중 실제 Top5에 들어간 개수다. 프로필별 후보 수가 다르고
  나머지는 미판정이므로 이 수치를 전체 추천 정확도나 프로필 간 우열로 해석하지 않는다.
- 점수 재현은 회귀 기준이고, 기대 쌍 충족은 품질 기준이다. 기준 결과를 재현한다고 모든 품질 기대가 충족된 것은 아니다.
- 변경마다 공고·프로필·모델/계산 버전·가중치를 함께 기록한다. 기존 입력/기대값은 보존하고
  새 버전 평가 세트를 추가한다. 승인 기준 갱신은 전체 변화와 이유를 검토한 뒤 명시적으로 수행한다.
- 운영 반영 전에는 필수 기술 우선·설명 일관성·장애 대체 동작을 유지하고, 의도한 개선과 악화를 모두 확인한다.
  이번 실험 후보는 개선과 악화가 함께 있으므로 **운영에 채택하지 않는다**.

## 첫 가중치 실험 결과

기준 35/20/20/15/10 → 후보 35/5/20/10/30(필수/우대/의미/경험/희망조건).
상세 내용은 [전체 비교 보고서](evaluation-v1-comparison.md)에 보관했다.

- 백엔드 신입: 서울 029가 제주 023보다 앞서도록 개선(60/65점 → 75/62.50점).
  동시에 필수 기술 완전 충족 015와 Spring Security 누락 017이 62.50점으로 동점이 되는 악화.
- 데이터 분석: 기대 쌍 2/4 → 4/4. 서울 004와 022가 우대 기술이 더 많은 타지역 공고보다 앞으로 이동.
- 프론트엔드: 기대 쌍 3/3 → 2/3. 필수 기술 완전 충족 008과 HTML 누락 012가 65점으로 동점.
  실제 표시 순서는 그대로여도 점수의 구분 능력이 약해졌으므로 악화로 판단한다.
- DevOps: 기대 후보 Top5 포함이 3개 → 2개로 감소. 지역만 맞는 다른 직무 공고가 올라오는 부작용.
- 문서 AI 의미 일치, 짧은 경력과 요구 연차 구분은 가중치만 바꿔도 해결되지 않았다.

3단계 의미 유사도 평가에서도 이 고정 세트를 재사용했다. 기술 정규화·기술 누락 설명은 유지하고,
업무 의미에 대한 개선과 아직 미충족인 기대 순서를 함께 기록했다.
