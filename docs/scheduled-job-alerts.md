# 관심 기업 공고 수집 및 이메일 알림 설계

작성일: 2026-10-12. Python 수집기, 알림 API·이메일 인증·SMTP 발송, 프론트 설정 화면과 Actions workflow를 구현했다. 실제 외부 수집과 발송은 아직 활성화하지 않았다. 현재 구현·한계와 설정 절차는 [실행 안내](../collector/README.md)를 따른다. 구현 검증에서 나온 문제와 처리 계획은 [검증 결과와 처리 계획](job-alerts-followups.md)에 정리했다. 아래 항목에는 후속 목표도 포함한다.

## 서비스 흐름

GitHub Actions 주기 실행 → Python 출처별 수집 → Spring Boot import API → PostgreSQL 저장 → 사용자별 추천 계산 → 이메일 발송 대기열 → 발송 결과 저장.

- 대상 출처: 사람인, 잡코리아, 원티드. 출처별 실패를 격리하고 다른 출처의 수집은 계속한다.
- 실행 주기: 매일 한국 시간(Asia/Seoul) 오전 11시와 오후 5시, 하루 두 번. GitHub Actions의 기본 UTC 기준 cron은 `0 2,8 * * *`이다. 수집 완료 후 신규 추천 공고의 이메일 발송을 처리한다. 승인받은 출처별 호출 속도와 API 한도는 각 실행에서도 준수한다.
- Actions는 반복 실행을 담당한다. 실행 간 공고·이메일 발송 이력은 운영 PostgreSQL에 보존한다. 수집 커서 영속화는 후속 목표다.
- 같은 기업·검색 조건을 합쳐 수집하고 사용자별 필터링과 추천은 백엔드에서 수행한다. Python runner에 개인 프로필·이메일을 전달하지 않는다.
- GitHub runner가 접근할 수 있는 HTTPS 백엔드가 필요하다. 로컬 PC의 localhost만 실행한 상태로는 연결되지 않는다.

## 출처 연결 상태

| 출처 | 확인된 경로 | 구현 전 필요한 정보 |
| --- | --- | --- |
| 사람인 | 공식 채용정보 API, 승인 후 access-key 발급 | OnFit의 저장·추천·이메일 활용 범위 승인, API 키 |
| 원티드 | 공식 OpenAPI의 기업 검색·기업별 포지션·Jobs | 채용공고 수집용 인증 신청, 발급된 계약·인증 규격 |
| 잡코리아 | 이번 확인으로 공고 수집용 공개 API나 사용 허가를 확정하지 못함 | 제휴 API/허용된 수집 경로와 명세, 저장·재게시 범위 |

미확인 경로를 승인된 것으로 표시하거나 웹 화면의 내부 요청 주소를 공식 API로 취급하지 않는다. 연결되지 않은 출처는 상태에 명시하며 전체 수집 성공으로 보고하지 않는다.

## 현재 코드에서 필요한 변경

- `JobImportService`의 출처 검증, 외부 ID 중복 방지, 변경 이력과 만료 처리를 재사용한다. 각 출처의 정책은 개별 등록한다.
- `RecommendationService.create()`는 로그인 사용자를 조회한다. 배치 작업에는 사용자 엔티티를 명시적으로 받는 내부 추천 서비스가 필요하다. 기존 사용자 API는 소유자 검사를 유지한다.
- `CurrentUser.identity()`가 생성하는 `oidc.…@onfit.invalid`는 내부 사용자 식별자다. `User.email`을 이메일 수신 주소로 사용하지 않는다.
- 프로필에 관심 기업 구독과 출처별 기업 ID 매핑을 추가한다. 기업 이름 키워드가 포함됐다는 이유만으로 해당 기업 공고라고 확정하지 않는다.
- 알림 설정에는 별도의 수신 이메일, 이메일 검증 상태, 수신 동의 및 해제 시각을 저장한다. OAuth에 실제 이메일이 없어도 로그인은 유지한다.
- Actions 호출은 전용 서비스 계정의 짧은 수명 토큰을 사용한다. 개인 로그인 토큰을 저장하지 않는다. 현재 `jobs:import` 권한으로 이메일 발송까지 허용하지 않고 알림 배치 권한을 별도로 둔다.

## 신규 추천 및 이메일 규칙

- 수신 동의와 검증된 이메일이 있는 사용자만 대상으로 한다.
- 실제 출처의 진행 중 공고만 대상으로 한다. 가상 시드, 마감 공고와 이미 발송한 공고는 제외한다.
- 관심 기업·희망 직무 조건을 통과한 공고를 기존 추천 점수로 정렬한다. 임시 점수 임계값을 정답처럼 고정하지 않고 평가 세트와 초기 사용자 평가로 결정한다.
- 최초 구독 시 기존 공고는 기본적으로 알림 기준선으로 등록한다. 이후 새로 확인된 추천 대상만 알린다. 처음부터 과거 공고 전체를 발송하지 않는다.
- 사용자별 신규 공고를 한 메일로 묶는다. 회사, 제목, 추천 근거, 마감 정보와 원문 링크를 포함한다.
- 동일 사용자의 동일 공고는 재실행·점수 변경만으로 재발송하지 않는다. 출처가 다른 동일 채용을 묶으려면 기업·포지션·원문 식별 근거가 있는 별도 중복 규칙이 필요하다.
- 발송 대기열에 `(subscription_id, canonical_job_id)` 유일 제약을 둔다. 추천 스냅샷 보존 기간과 발송 이력 보존 기간을 분리한다.
- 대기열에는 상태, 시도 횟수, 다음 시도 시각과 전송 ID를 기록한다. 공급자가 idempotency key를 지원하면 활용한다.
- SMTP에서 서버 수락 직후 프로세스가 죽으면 발송 여부가 불명확할 수 있다. SMTP만으로 정확히 한 번 전송을 보장한다고 설명하지 않는다. 불명확한 상태는 자동 무한 재시도하지 않는다.
- 구독 해제와 마감 상태를 실제 전송 직전에 다시 확인한다.

## 운영과 검증

- Actions workflow에는 수동 실행, 실행 시간 상한, 중복 실행 방지(concurrency)를 둔다. 승인된 요청 속도와 일일 한도를 출처별로 제한한다.
- API 키·서비스 계정 비밀값은 GitHub Secrets, 이메일 전송 비밀값은 운영 백엔드의 비밀 저장소에 둔다. 토큰·메일 주소·공고 전체 본문을 runner 로그나 artifact로 남기지 않는다.
- 수집 성공 시각, 출처별 실패·부분 수집, 대기열 적체와 발송 실패를 기록한다. 스케줄 지연 시 다음 실행은 마지막 성공 커서부터 재개한다.
- 동일 수집 두 번과 겹친 실행에서 공고·대기열 중복이 없어야 한다.
- 신규 적합 공고, 부적합 공고, 마감 공고, 이메일 미검증, 구독 해제, 한 출처 장애, 이메일 장애와 재시도를 테스트한다.
- 배포 DB의 마이그레이션과 테스트용 이메일 공급자 검증 후 실제 발송을 활성화한다.

## 확인한 공식 자료

- [사람인 API 사용안내](https://oapi.saramin.co.kr/guide/info): 승인 후 키 발급, 현재 안내상 하루 최대 500회 호출.
- [원티드 OpenAPI](https://openapi.wanted.jobs/): 인증 신청과 기업·채용공고 API 안내. 구체적인 이용 범위는 발급 계약과 명세를 확인한다.
- [GitHub Actions schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule): 기본 브랜치에서 실행하며 혼잡 시 지연·누락될 수 있다. 공개 저장소에서 60일간 활동이 없으면 스케줄이 비활성화될 수 있어 별도 실행 감시가 필요하다.
